# 黒にんにく管理 GitHub Pages + Supabase版

Google Apps Script版の機能を、GitHub Pagesで配信できる静的HTMLとSupabaseのテーブルに移すための初期実装です。

## 構成

- `index.html` - 画面本体
- `styles.css` - 冷蔵庫管理に寄せたモバイル優先UI
- `app.js` - 入力、履歴、集計、予測、マスタ編集
- `config.js` - Supabase URL / anon key の固定設定
- `supabase/schema.sql` - テーブル、初期データ、RLS、権限
- `supabase/rpc.sql` - 在庫再計算、在庫監査などの補助RPC
- `supabase/common-auth.sql` - 共通ログインの書き込み権限チェック

## 初期設定

1. Supabase SQL Editorで `supabase/schema.sql` を実行する
2. 続けて `supabase/rpc.sql` を実行する
3. `config.js` にSupabase URLとanon keyを入れる

```js
window.APP_CONFIG = {
  supabaseUrl: "https://xxxxx.supabase.co",
  supabaseAnonKey: "eyJ..."
};
```

接続設定は `config.js` の固定設定を使用します。端末ごとの接続設定画面はありません。

## 共通メニューからのログイン

- [業務管理メニュー](https://eight-corp.github.io/garlic-liff-scanner/menu.html?openExternalBrowser=1) で作業者と共通PINを使ってログインし、室管理を開きます。
- 室管理は共通セッションをサーバーで検証し、その作業者を登録者として使用します。独自PIN保存や作業者切り替えはありません。
- 未ログイン、期限切れ、利用権限がない場合はメニューに戻ります。
- 「メニュー」はログインを維持して戻り、「ログアウト」は共通セッションを破棄して戻ります。
- 閲覧者は履歴・集計・予測の閲覧、作業者は登録・編集・削除と予測設定、管理者はさらにマスタ編集を行えます。
- 共通認証を導入したSupabaseで、対応画面の公開後に `supabase/common-auth.sql` を実行します。既存データは変更せず、室管理テーブルの書き込み権限を共通認証で検証します。

`tests/common-auth.cjs` はPlaywrightとChromeで共通メニューからのログイン、登録者、権限、期限切れ、ログアウトを検証します。通信とデータ書き込みはすべてテスト用に置き換えます。共通メニューのソースは隣接する `garlic-liff-scanner-repo`、または環境変数 `COMMON_MENU_REPO` で指定します。

環境変数 `USE_PUBLISHED_SOURCE=1` を指定すると、画面のソースはGitHub Pagesの公開版を使います。この場合もSupabase通信と書き込みはテスト用に置き換えます。

`tests/common-auth-rollback.sql` は適用後のSQL Editor用の権限テストです。既存レコードを使った試験変更は最後にすべてロールバックします。

## データ構造の考え方

- 作業者は冷蔵庫管理と同じ `workers` を共有します。
- 黒にんにく用のデータはすべて `black_garlic_` 接頭辞のテーブルに分離しています。
- 黒にんにく入力は `日付 + 室名 + 種別 + 収穫ロット` の組み合わせで上書きします。
- 在庫は `室名 + 種別 + 収穫ロット` 単位で、前回在庫 - 出庫 + 入庫により再計算します。
- 在庫欄に値を入力した行は手入力フラグを立て、その行を基準点として以降を再計算します。
- 出庫予測は `室名 × 収穫からの経過日数区分` の熟成日数表を参照します。

## 収穫基準日と出庫予測

- マスタの見出しは「室名」「種別」「保管種別」「熟成日数表」です。「種別」の各項目に「収穫基準日」を設定し、「確定」で保存します。追加・名称変更・並べ替えなどの操作中は仮入力を維持し、確定前は予測に反映しません。
- 室名・種別の各項目はスマホでも1行です。幅760px以下またはタッチ端末では番号と表示スイッチの文字を省き、種別の日付は `26/09/12(土)` の省略表記で表示します。内部の日付は元の年月日を保持し、日付欄全体からネイティブの日付選択を開けます。収容能力・並べ替え・表示切替・削除の機能は維持します。
- 設定は既存の `black_garlic_settings` に `setting_key = maturation`、`setting_value.harvestBaseDates = { 種別ID: YYYY-MM-DD または空文字 }` として保存します。追加のSQLは不要で、日平均使用列数の `prediction` 設定とは別に管理します。種別IDで管理するので名称変更・並べ替え・非表示でも日付がずれません。
- 旧共通設定 `harvestBaseDate` は種別ごとの設定がない既存種別に引き継いで表示・計算し、次の「確定」で各種別の設定に置き換えます。新規追加した種別は空欄から開始し、削除した未使用種別の日付も設定から除去します。空欄にして確定した種別には旧共通日付を再適用しません。
- 各入庫の `入庫日 - その種別の収穫基準日` を経過日数とし、開始・終了日数を含む区分の熟成日数を室別に参照します。予測出庫日は `入庫日 + 熟成日数` です。基準日当日は0日で、今日までの経過日数によって過去の入庫の区分が毎日変わることはありません。
- 収穫基準日が未設定・空欄の場合は従来どおり各レコードの収穫ロットの日付を参照します。該当する区分・室別の熟成日数がない場合は30日を使います。基準日より前の入庫も、負の日数に一致する区分がないため30日です。
- 熟成日数の0日は当日出庫として扱います。確定後は予測表とグラフを再計算し、入出庫・保管庫・在庫データ自体は変更しません。

## 集計の表示

- 日毎集計は廃止し、室と保管庫の週毎・月毎を独立したタブに分けています。日付が縦、室名または保管庫種別が横、右端が合計です。
- 週毎は集計開始日を含む週（初期値は今週）と先週の2表を、今週・先週の順に表示します。各表の日付は上から月曜〜日曜の昇順です。月毎はその月の1日〜月末の枠を表示します。
- 週毎・月毎とも当日より未来の行は日付・数値・合計を空欄にします。月毎の保管庫集計も同じです。未来日の元データは変更せず、当日になったら表示します。
- 室の表示項目は出庫数・入庫数・空き・在庫から1つ選択し、週毎と月毎の切り替えでも選択を維持します。種別・室名の絞り込みも共通です。保管庫では室用の絞り込み・表示項目を隠し、表示設定が有効な保管庫種別を上段16段・下段端数で集計します。記録がない日は空欄とし、室の在庫のような繰り越しは行いません。
- 在庫は各日時点の最新在庫を表示し、記録のない日には直前の在庫を引き継ぎます。合計は表示中の室の合計で、日をまたいだ在庫の累計ではありません。
- 画面下の集計切り替えは「週毎(室)」「週毎(保管庫)」「月毎(室)」「月毎(保管庫)」「グラフ(室)」「グラフ(保管庫)」の順です。室・保管庫の表は集計開始日を共有し、保管庫の週毎も対象週と先週の2表です。

## グラフの表示

- 室の実績グラフは「集計」の「月毎(保管庫)」の右の「グラフ(室)」に配置しています。その右に「グラフ(保管庫)」を配置しています。上位の「グラフ」タブには出庫予測だけを残しています。
- 保管庫グラフは表示期間・更新・全画面の下に5系列の保管種別・表示形式を配置します。一つ目は黒色の「全体」固定で、残り4系列は表示状態の保管種別マスタから選択します。初回は上から4種別を選び、以後は選択を保持します。幅460px以下では全体を1行、残り4種別を次の行にまとめます。「非表示」を選んだ系列やマスタで非表示・削除された種別は描画しません。各系列は独立して折れ線・棒グラフを選べ、同じ種別を複数系列で選んでも全体の合計は二重になりません。保管数は `16段 + 端数 / 16` の列数です。表示期間の初期値は1か月前から1日後で、室グラフと別管理です。各保管種別の最新値を日ごとに持ち越し、記録がない期間と未来は空欄です。全画面表示・回転対応・選択系列と期間を載せた印刷を利用でき、入出庫・室マスタ・在庫計算・予測データ自体は変更しません。
- 室の実績は入庫・出庫が棒グラフ、在庫は緑色の折れ線が初期値です。3項目それぞれを折れ線・棒グラフから選べ、在庫は右側の数量軸を使います。収容率の系列・計算・％軸・選択欄は削除し、室名マスタの収容能力設定は残しています。全画面表示・印刷・種別と室名の絞り込みを維持し、週毎・月毎の操作欄は非表示です。
- スマホの実績グラフは種別・室名・開始日・終了日・更新・全画面を1行に配置します。日付は `26/09/14` の省略表記で、内部には元の年月日を保持し、タップでネイティブの日付選択を開きます。幅760px以下または主操作がタッチの端末に適用し、横向きでも維持します。PCでは従来の2段配置です。折れ線・棒グラフの選択は別の行に残します。
- 予測側は出庫予測グラフを初期表示し、「予測出庫数」で表も参照できます。熟成日数表・収穫基準日・日平均使用列数による計算は従来どおりです。
- 実績と予測の表示期間・種別・室名は独立して保持します。集計の絞り込みとは別管理で、タブの切り替えではデータや予測設定を書き込みません。
- 予測保管数は表示開始日前の最新保管数の数値を初期値として引き継ぎます。今回、合計を含むオブジェクトを数値として扱ってしまう既存の不具合を修正しました。
- 実績グラフの全画面表示中は縦横の向き・表示領域の変更後に再描画します。タッチ端末で対応しているブラウザではグラフ要素だけをネイティブ全画面表示にし、`screen.orientation.lock("any")` で自動回転を許可します。終了・戻る・タブ切り替え・印刷では解除し、通常画面や他のタブに回転制御を追加しません。
- LINE内ブラウザなどでネイティブ全画面表示や向きの制御が拒否される場合は従来の全画面ダイアログを維持します。この場合や端末の回転ロックが優先される場合、端末の自動回転を有効にする必要があります。画面方向が通知されない環境で、センサー権限を要求したりグラフを強制回転したりはしません。

## 注意点

- マスタの「室名」にある「収容能力」は在庫と同じ数量単位の目安です。空欄は未設定、0以上の小数を設定でき、超過しても入庫・在庫の登録や計算を制限しません。「確定」で保存します。
- 収容能力は既存の `black_garlic_settings` テーブルの `roomCapacities` に `{室ID: 数量}` として保存します。SQL実行やテーブル変更は不要です。室名の変更・並べ替え・非表示で値を引き継ぎ、室の削除や収容能力を空欄にして確定した場合は対応する設定を削除します。

GitHub Pagesから直接Supabaseテーブルを操作します。`supabase/common-auth.sql` の適用後は、室管理の書き込みに共通セッションと操作権限が必要です。読み取りは既存のRLS設定を維持するため、メニューのログインだけですべてのAPIの閲覧が制限されるわけではありません。

## GitHub Pagesへの配置

- リポジトリ: [eight-corp/black-garlic-manager](https://github.com/eight-corp/black-garlic-manager)
- 公開URL: [黒にんにく室管理](https://eight-corp.github.io/black-garlic-manager/)
- Pagesの公開元: `main` ブランチの `/` (ルート)

ビルド処理は不要です。画面の更新はこのリポジトリに反映します。Supabaseの接続先とデータは移管前と同じです。

共通メニューと室管理は同じ `eight-corp.github.io` の保存領域を使用します。メニューのログインは同じブラウザ内で共有されます。LINE内ブラウザとChromeなど、異なるブラウザ間では共有されません。
